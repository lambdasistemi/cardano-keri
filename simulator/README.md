# Play the M1 identity model

As an identity owner, register, rotate, unfreeze and top up a checkpoint while
following its key state and addressed payments. There is no owner exit: a
checkpoint is alive until it is convicted. As a relying party, inspect
why a checkpoint is unusable. As a folder, inspect the complete transaction
and pending request that make a Registry transition possible.

Open `checkpoint-simulator.html` or `registry-simulator.html` locally. Their
copies in `docs/simulator/` are generated byte for byte. Both pages work without
network requests and offer light/dark themes, story playback, branches and
editable actions. These are executable model adapters, not transaction builders.

## Three execution surfaces

| Surface | Authority | What is compared |
| --- | --- | --- |
| Checkpoint local player | `Checkpoint.stepFn` and local theorem premises | Full next state and addressed flow, consumer verdict, 12 played stories (15 numbers, 3 retired) and branches |
| Registry player | `Registry.stepFn` and the imported Singular economic judgments | Complete booking/transaction context, full successor world and application flow |
| Checkpoint associated-system panel | Actual `SysStep` certificates under stored context | Registration origins, whole pending entries, exact consuming receipts, both flow records |

There is no close, no parked state and no revival. Conviction is pending until the associated fold
consumes its exact request; it does not immediately retire the key. The local
player cannot establish that final boundary alone. Use its **associated system**
panel to select a connected journey, step through its full states and receipts,
or edit the next command. An edited command has no matching Lean oracle cell
unless it is one of the generated cases.

`M1-STORIES.md` is the canonical Checkpoint reader register;
`REGISTRY-STORIES.md` is the Registry register. Stable story IDs are kept even
when the ruling changes their behavior. `checkpoint-story-migration.json` and
`registry-story-migration.json` record those dispositions. JSON and `.dsl`
scenarios share one grammar in `scenario-dsl.mjs`; the page and CLI load it.

## Model observations and test scope

Checkpoint wire v2 contains six traces, a 750-cell local grid, theorem and
consumer observations, and 60 story action cells. Together its local action
observations contain 157 accepted and 688 refused results. Local session
multi-AID checks exercise frames; they do not claim SysStep reachability.

Registry wire v3 contains six connected traces, a 12-cell local grid, 161
economic boundary cells and 12 played stories (15 numbers, 3 retired) with 19
forks and 64 story cells: 477 complete observations, 94 accepted and 383
refused. Its model census lists 125 decision sites and 104 refusal reasons: 95
have executable witnesses
and nine have separately proved construction exclusions. This is reason-level
coverage, not proof that every repeated branch site was executed.

The associated Checkpoint system has four connected traces and 33 complete
cells, 22 accepted and 11 refused. It includes stored-context replay, another
valid request that cannot complete the selected identity, and a mixed fold
that can. Eight properties are evaluated only on actual system events.

Kernel proofs, finite model executions, compiled model mutants, JavaScript
implementation mutants and fabricated property-checker failures are distinct.
No finite replay establishes cryptographic verification, deployed conformance
or complete consumer transaction authorization.

Safe JSON integers are numbers; larger model naturals are decimal strings in
the Registry/system wire profile. The interpreter uses exact integers. Malformed
schema input and a well-formed model refusal are different outcomes.

## Generate and check

Use the project's Lean toolchain (`lean/lean-toolchain`) and resolve its pinned
Singular dependency before running the drivers. `LAKE_BIN` selects that Lake
binary for the trace gates; no floating compiler is required.

```sh
node simulator/checkpoint-simulator-build.mjs
node simulator/registry-simulator-build.mjs
node simulator/scenario-dsl-gate.mjs
node simulator/checkpoint-simulator-scenario-gate.mjs --selftest
node simulator/registry-simulator-scenario-gate.mjs --selftest
node simulator/checkpoint-simulator-trace-gate.mjs --selftest
node simulator/registry-simulator-trace-gate.mjs --selftest
node simulator/checkpoint-system-checks.mjs
node simulator/checkpoint-system-page-checks.mjs
node simulator/checkpoint-system-trace-gate.mjs --selftest
node scripts/check-architecture-scenarios.mjs --selftest
```

The trace gates rebuild imports, execute fresh Lean, compare committed and
embedded corpora and replay full results through the cores and pages. Cold
controls first demonstrate that missing imports fail, then rebuild and require
identical output. A setup or compilation error is not a semantic mutation kill.

The local property gate has one declared row per local theorem or inversion;
system rows are checked against the associated system. Fabricated violations
check that those property checkers can fail. Story clauses and source digests
must be refreshed only after checking their actual meaning.

After source changes, regenerate both pages and rerun the affected trace,
scenario, CLI, template and browser checks. `--check` on each builder detects
stale copies. The architecture gate also verifies the rendered DSL text and
downloads after a strict documentation build.

## Limits

Registry local evidence remains coarse; Checkpoint carries its separate
concrete duplicity and signed intent predicates. The associated certificate
adapter requires the actual stored origin and exact request receipt. It is
not a proof that the two models' evidence predicates are equivalent.

Production Aiken, Haskell, `ckeri`, deployment and releases require their own
correspondence evidence. Exact token/canonical registry and consumer validity
work is tracked by #439; broader application request recovery by #468.
